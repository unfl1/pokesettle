# 요구사항 분석 및 단계별 개발 계획

작성일: 2026-10-21 (Asia/Seoul). 이 문서는 Phase 0 설계 기준이다. **Phase 1 구현·실행 결과는 [TEST_RESULTS.md](TEST_RESULTS.md)를 참조한다.** 아래 '구현 전' 기록은 Phase 0 당시의 상태이며 현재 상태와 구별한다.

> 현재 구현 상태: Phase 0의 아래 “미확인” 표기는 당시 설계 기록이다. Phase 1 데이터·RAG와 Phase 2 대화 UI·통합을 실행 검증했으며 최신 판정은 [Phase 2 결과](PHASE2_RESULTS.md)를 참조한다. Champions 규칙·적격성과 외부 상호 점검은 여전히 미확인이다.

## 2. 서비스와 도메인 적합성

PokéCoach AI는 포켓몬을 선택해 문서 근거가 있는 전략 질문을 하고, 조건에 맞는 포켓몬을 찾는 RAG 지식 서비스다. 주 사용 목적은 랭크 싱글 준비와 대전 복기다.

| 과제 조건 (PDF 4, 7쪽) | 확보 방안 | 현재 확인 수준 / 통과 조건 |
|---|---|---|
| 속성이 있는 약 100건 이상 항목 | PokéAPI 기초 종·폼 정보를 정규화하고 중복 없는 기본 포켓몬 100건 이상 확보 | API 문서 확인, 실제 확보 0건. 폼만 늘려 수량을 채우지 않는다. Phase 1에서 로드·색인 수를 증명 |
| 항목별 외부 설명 문서 | 종별 설명 문서와 연결 ID를 확인하고, 사용 조건이 확인된 위키/API/제공 문서 묶음에서 수집 | 출처 후보 확인. 100종의 개별 문서 커버리지와 권리 확인은 미완료 |
| 근거가 필요한 질문 | 아래 질문처럼 규칙·조건·출처에 따라 답이 달라지는 질문 | 질문 예시 정의 완료, 답변 품질은 미검증 |

질문 예시:

1. 선택한 포켓몬의 특정 폼이 지정 레귤레이션에서 사용 가능한가? 공식 근거는 무엇인가?
2. 이 포켓몬의 운용 가이드에서 전제한 기술·특성은 Champions에서도 확인되었는가?
3. 땅 타입 공격을 받지 않는다고 설명한 근거는 타입인가, 특성인가? 예외 조건은 무엇인가?
4. 일반적인 역할 설명이 싱글 기준인가, 더블이나 과거 게임 기준인가?
5. 이 상대에게 메가진화가 유리하다고 단정할 자료가 있는가? 미공개 정보는 무엇인가?

건강·금융 도메인 면책은 해당하지 않는다. 대신 검증 수준·게임 적용 범위·미확인 정보를 표시한다. 현재 경기 중 외부 도구 사용 허용 여부는 검증되지 않았으므로 준비·복기 범위로 설계한다.

PDF의 '1일차 16시까지 100건 확보 실패 시 영화 팩 전환'은 교육 일정 조건이다. 해당 교육 일정은 제공되지 않았다. 도메인을 임의 변경하지 않으며 Phase 1 첫 작업에서 확보 가능성을 확인하고, 실패하면 원인과 과제 조건을 보고한다. **포켓몬 도메인의 조건을 이미 충족했다고 주장하지 않는다.**

## 5. 범위와 기술 결정

- Python 기반 RAG를 중심으로 React/TypeScript/Vite/Tailwind UI와 FastAPI를 연결한다. PDF 5쪽은 Streamlit을 준비 기술로 명시하고, 16쪽 F2013은 화면·서버 분리와 HTML/CSS/JavaScript UI를 허용한다. React 경로는 `PROJECT_SPEC.md`에 따른 F2013 구현 제안이며 담당자 수용 여부는 미확인이다. Streamlit 필수 제출 여부는 구현 착수 시 확인할 과제 해석 위험으로 기록한다. 지금 대체 UI를 추가하지 않는다.
- PDF는 LangSmith를 필수 라이브러리 목록에 포함하지만 제품 명세는 선택으로 적었다. 의존성 검토는 PDF를 우선하고, 원격 트레이싱 사용은 별도 환경·정책 검토 대상으로 둔다.
- F2014 MMR, F2015 RAG 전후 비교, F2016 복수 출처 유형은 심화다. 데이터 모델은 출처 유형을 지원하되 필수 완료 전에 심화 개발을 시작하지 않는다.
- 폼/기술/아이템 적격성, 레벨, 육성 방식, 데미지 공식은 검증 전 동작 규칙으로 고정하지 않는다.

## 6. 단계별 실행 계획과 종료 기준

기간은 작업 순서이며 확정 일정이 아니다. 각 단계는 별도 사용자 요청 후 시작한다.

| 단계 | 작업 순서 및 산출물 | 종료 조건 / 다음 단계 전제 |
|---|---|---|
| Phase 0: 설계만 | 세 문서 조사→필수 매핑→출처 조사→아키텍처·데이터·API·위험 설계. 현재 네 문서 | 설계 간 일관성 검토 완료. 구현·수집 실행 없음. 이후 중단 |
| Phase 1: 필수 RAG 데이터·백엔드 | ① 버전/교육환경·100건 확보 가능성·자체 문서·권리 확인 ② 데이터 검증 ③ 메타 색인 ④ Prompt 1·2/수집/캐시 ⑤ 청킹/문서 색인 ⑥ retrieve/generate·Prompt 3/인용 ⑦ API·작업 상태·백엔드 검증 | F2001~F2008 백엔드 증거, 동일 입력 재색인·무근거 유보·캐시 검증. 데이터 확보/권리/패키지 문제는 차단 항목 보고. 화면 증거는 Phase 2에서 보완 |
| Phase 2: 필수 UX·통합 | ① React 화면 ② 항목 선택·채팅·기록 ③ 자연어 탐색 ④ 인용 운용 가이드 ⑤ 진행/오류 ⑥ 전체 필수 및 NF 검증 | F2001~F2012와 NF 전체 체크리스트, 화면 캡처, README, 셀프/상호 점검. React 과제 수용 여부 해소 |
| Phase 3: 배틀 보조 | 규칙 검증→팀 저장/적격성→타입 상성→선출 후보→공격·교체·메가 시나리오 | 검증된 규칙만 계산, 가정·미공개 정보 표시. 휴리스틱을 승률로 표시하지 않음 |
| Phase 4: 선택 심화 | Champions 계산 라이브러리 검증 후 데미지/조건부 KO. 별도 선택 시 MMR·복수 출처·비교 평가 | 선택 기능별 근거와 검증. F2015 선택 시 동일한 대표 질문 >=5개로 정확성·출처·유보 비교 |

각 단계 보고 형식: 변경 파일, 실행한 검증과 결과(통과/실패/미확인), 요구사항 ID, 남은 차단 사항, 다음 요청 범위. 제출 시 PDF 18~23쪽에 따라 설계·코드·수집/색인 절차·검증표·화면·README·셀프 및 상호 체크리스트를 준비한다. 실측/실행하지 않은 증거는 미확인으로 남긴다.
